Статус: сервер, схема пустой БД и желаемый поток CI/CD определены; CI/CD-шаблон подготовлен, публичный запуск и эксплуатационная проверка не выполнены.

Пользователь предложил домен приложения `app.traineeserver.ru`. Read-only DNS lookup 2026-11-07 показал A-записи `traineeserver.ru` и `app.traineeserver.ru`, обе указывают на `77.232.129.164`. Веб-приложение на этих адресах ещё не проверялось и не опубликовано.

Deploy SSH-подключение с локального компьютера проверено: пользователь `meeting-deploy` входит по отдельному ключу, состоит в группе `meeting-analysis`, а `sudo -n -l` показывает только `/usr/bin/systemctl restart meeting-analysis`. Fingerprint серверного ED25519 host key, прочитанный на VM: `SHA256:YUhazrYpDCw2C22FmxcbPxX/M7pcqAnRjPqWEQExB0k`.

## Целевой сервер: инвентаризация (проверено 2026-11-07)

Владелец проекта предоставил сервер `77.232.129.164` для публикации: Ubuntu 26.04.1 LTS, 1 vCPU 3.3 ГГц, 2 ГБ RAM, 20 ГБ NVMe. Доступ по SSH подтверждён. Корневые секреты/ключи в документах не сохраняются.

Снята только read-only инвентаризация:

- свободно около 1,2 ГиБ RAM и 14 ГБ на `/`; swap не настроен;
- слушает SSH на TCP/22 и Zabbix agent на `0.0.0.0:10050`; UFW выключен;
- Python 3.14.4 есть; FFmpeg/FFprobe 8.0.1 установлены владельцем; Nginx пока не установлен (доступен в APT: 1.28.3); каталоги `/opt`, `/srv`, `/var/www` были пусты при первичной инвентаризации;
- APT-репозитории Ubuntu 26.04 сейчас не предлагают `python3.12`/`python3.12-venv`. Проект рассчитан на Python 3.12, значит нужно отдельно поставить runtime 3.12 (например, управляемый `uv` runtime либо подготовленный образ) и не запускать проект на системном Python 3.14 без проверки совместимости;
- на сервере работают системные службы и агент мониторинга; их настройки не менялись.

### Принятое решение по серверу пилота

Для ограниченного пилота использовать **один процесс приложения, SQLite и постоянный локальный каталог данных**, без установки PostgreSQL/Redis на эту VM. Медиа имеют лимит 25 МБ и срок хранения 24 часа, но нужно ограничить число параллельных обработок и настроить очистку/бэкапы. На 20 ГБ необходимо оставить запас для ОС, релизов, логов и резервных копий; локальный диск не является надёжной единственной копией данных.

Перед публичным доступом требуется отдельно решить вопрос периметра: сейчас UFW неактивен, SSH и Zabbix agent слушают внешний интерфейс. Не менять firewall до согласования доступа и проверки фильтрации в панели провайдера, чтобы не потерять SSH/мониторинг. Порт 10050 не должен оставаться доступным из интернета без нужды.

**Решение владельца для пилота:** использовать эту VM с SQLite и локальным постоянным диском; PostgreSQL и S3 сейчас не подключать. Публичный IP не записан в `DECISIONS.md`.

### Подготовленные локальные шаблоны

- `ops/systemd/meeting-analysis.service` — одиночный Uvicorn worker, loopback-only listener, данные в `/var/lib/meeting-analysis`, отдельный системный пользователь, секреты из локального `/etc/meeting-analysis/.env`.
- `ops/nginx/meeting-analysis.conf.example` — HTTP→HTTPS, загрузка до 26 MiB, proxy только на loopback и блокировка `/setup` с публичного домена.
- `ops/meeting-analysis.env.example` — названия и значения-заглушки переменных без реальных секретов.
- `.github/workflows/deploy-pilot.yml` — GitHub Actions: push в `main` → передача исходников на сервер по SSH → активация релиза.
- `ops/deploy-release.sh` — серверный переключатель релиза, установка закреплённых зависимостей, перезапуск systemd, проверка `/health` и откат ссылки на предыдущий код при ошибке.
- `ops/sudoers/meeting-analysis-deploy` — ограниченное разрешение deploy-пользователю только на перезапуск сервиса.
- `requirements.lock` — точные версии зависимостей из локального Python 3.12 окружения для серверной установки.

Systemd unit установлен на сервере, но первый релиз и Nginx ещё не установлены. Nginx требует заменить доменное имя и получить сертификат. Для первого создания администратора потребуется SSH-туннель напрямую к loopback приложения, так как публичный `/setup` закрыт в Nginx. Python 3.12 runtime и venv уже размещены в `/opt/meeting-analysis`; системный Python 3.14 не используется.

### Поток обновления через GitHub

Workflow запускается на каждый push в `main`, но job намеренно пропускается, пока GitHub variable `PILOT_DEPLOY_ENABLED` не установлена в `true`. Он использует официальный `actions/checkout`, закреплённый на полном commit SHA. Перед упаковкой отслеживаемых файлов workflow откажется продолжать, если обнаружит `data/`, `.env` или другой `.env.*` файл (кроме `.env.example`). Файл `data/` и локальный `.env` в архив релиза не попадают; база на сервере остаётся на месте.

Настройки репозитория GitHub → Settings → Secrets and variables → Actions:

**Variables**

- `PILOT_DEPLOY_ENABLED` — сейчас `false`; установить `true` после первого ручного развёртывания и проверки.
- `PILOT_DEPLOY_HOST` — `app.traineeserver.ru`.
- `PILOT_DEPLOY_USER` — `meeting-deploy`.

**Secrets**

- `PILOT_SSH_PRIVATE_KEY` — отдельный SSH private key deploy-пользователя; соответствующий public key добавляется на сервер только этому пользователю.
- `PILOT_KNOWN_HOSTS` — verified SSH host-key line для `app.traineeserver.ru`; fingerprint сверить с SSH host key fingerprint на сервере, не доверять непроверенному `ssh-keyscan` результату.

OpenAI key и `APP_SECRET_KEY` должны храниться в root-only файле окружения на сервере, не в GitHub workflow и не в Git. Deploy-пользователь пишет только в `/opt/meeting-analysis`; для read-only проверки статусов он включается в группу `meeting-analysis`. `sudoers` разрешает ему только `systemctl restart meeting-analysis`.

Workflow реагирует только на push в `main` (в том числе после merge pull request), не запускается на pull request и не выполняет тесты. В общем репозитории защищайте `main` от непроверенных изменений: workflow получает deploy SSH key. Деплой сначала проверит, что в SQLite нет встреч со статусом `processing_*`; если обработка активна, workflow завершится с просьбой повторить после её завершения. Между этой проверкой и рестартом остаётся короткое окно для новой загрузки, а обновление кратко перезапускает приложение.

## Последовательность установки (ещё не выполнялась)

1. Использовать `app.traineeserver.ru` и проверить A-запись перед выпуском сертификата; определить доступ к TCP/80 и TCP/443 через панель провайдера.
2. Установить Python 3.12 runtime отдельно от системного 3.14 и создать venv через `uv venv --seed` (скрипт деплоя использует `pip`); FFmpeg/FFprobe уже установлены, Nginx установить перед HTTPS-настройкой.
3. Создать системного пользователя `meeting-analysis`; код разместить в `/opt/meeting-analysis/current`, venv — в `/opt/meeting-analysis/venv`, данные — в `/var/lib/meeting-analysis`. Каталог данных должен быть новым и пустым перед первым запуском, чтобы приложение создало чистую SQLite-базу.
4. Разместить env-файл вне репозитория с `APP_SECRET_KEY`, `OPENAI_API_KEY` и остальными переменными; права файла — только root. Не копировать локальный `.env` или `data/` с рабочего проекта: сервер начинает с пустой БД, без локальных пользователей, приглашений, встреч, транскриптов и медиа.
5. Настроить systemd unit, сначала проверить локальную доступность `/health`, затем настроить сертификат и Nginx. Публичный `/setup` оставить заблокированным; создать администратора по SSH-туннелю.
6. Настроить deploy-пользователя, sudoers, GitHub variables/secrets; сначала выполнить ручной deploy, проверить его и только затем включить `PILOT_DEPLOY_ENABLED=true`.
7. До публичного запуска проверить снаружи, что открыты только необходимые порты (HTTPS и выбранный SSH; TCP/10050 закрыть публично, если его не требует мониторинг), затем проверить Secure cookie, загрузку/обработку реальной записи, права пользователей, очистку медиа, бэкап и восстановление.

Пункты 1–7 требуют настройки и проверки перед публикацией. На VM уже подготовлены deploy-пользователь, FFmpeg, Python 3.12, venv, секретный env-файл и systemd unit; в GitHub заданы repository variables и secrets. Первый релиз, Nginx и HTTPS ещё не настроены.

## Текущее состояние

Проект работает как локальный прототип. До публикации в интернете нужно закрыть блокеры ниже. Текущую сборку нельзя запускать несколькими Uvicorn workers или репликами: фоновые задачи выполняются внутри веб-процесса, а SQLite и медиа находятся на локальном диске.

## Блокеры публикации

1. **Подготовить runtime.** Python 3.12 нужно установить отдельно от системного Python 3.14; установить FFmpeg/FFprobe.
2. **Обеспечить восстановление обработки.** Для пилота принят ручной повтор встречи после прерывания. Каждая задача выполняется в процессе FastAPI; при рестарте отмечается неуспешной. Не запускать несколько workers/реплик.
3. **Убрать зависимость от `.env` на сервере.** Передавать секреты через защищённое окружение сервиса. `APP_SECRET_KEY` должен быть задан до импорта приложения: при пустом значении прототип записывает ключ в `.env` рядом с кодом.
4. **Настроить периметр.** Нужны домен, HTTPS, reverse proxy, автоматическое продление сертификата, ограничение размера тела запроса не ниже multipart лимита приложения (26 MiB), таймаут загрузки и корректная передача `X-Forwarded-Proto`.
5. **Проверить безопасность и эксплуатацию.** Первичного администратора создать по защищённому SSH-туннелю; публичный `/setup` закрыть в proxy; задать `COOKIE_SECURE=true`; проверить роли и логи без содержимого видео/транскриптов. Не допускать публичный доступ к TCP/10050.
6. **Настроить резервирование.** Регулярно копировать SQLite и текстовые результаты на отдельное хранилище, задать срок хранения резервных копий и проверить восстановление. Медиа удалять согласно принятому 24-часовому сроку; очистка по событию приложения требует отдельного контроля.

## Целевая схема после выбора инфраструктуры

- Linux VM с Python 3.12, FFmpeg/FFprobe и systemd.
- Nginx или эквивалентный reverse proxy с HTTPS и ограничением upload body.
- Один веб-процесс до замены встроенных фоновых задач на отдельную устойчивую очередь.
- Постоянные приватные данные вне каталога релизов; секреты не в Git и не в файлах репозитория.
- База и объектное хранилище выбираются отдельно и документируются в `DECISIONS.md` после согласования.
- `/health` используется для проверки процесса; дополнительно нужен мониторинг доступности и свободного диска.
